### P-01 新しいリポジトリを作成できなかった（要対応）

【問題】
この作業環境の GitHub 連携には、新しいリポジトリを作る権限がない（作成を試みたが拒否された）。

【影響】
設計書を新しいリポジトリに移せない。現在は家計管理アプリのリポジトリの作業ブランチ上（公開対象外の `docs/` 配下）に置いたままになっている。

【推奨変更】
次の手順で移す。
1. ご自身で GitHub に空の非公開リポジトリ `baseball-life-sim` を作成する（README なしでよい）
2. Claude の GitHub App がそのリポジトリにアクセスできるようにする
3. 作成後に知らせてもらえれば、この作業から接続して設計書を移し、家計管理アプリのリポジトリからは削除する

【代替案】
新しいリポジトリを選んだ状態で新しいセッションを始め、そこで設計書を作り直す（この作業ブランチの内容をコピーする）。

### P-07 リセマラ対策とセーブの自由（未決定 → D-09）

【問題】
仕様 §81 は「ロードし直しが最適解にならない」ことを求めているが、§66 は複数スロットのセーブを想定している。

【影響】
セレクション直前にセーブして、結果が悪ければやり直すことができる。

【推奨変更】
- 乱数を「何の・誰の・いつの」で決まる方式にする（設計書 §3.5）。同じ判断をすればロードし直しても同じ結果になるので、結果を変えるには準備や判断を変える必要がある
- 難易度 REALISTIC では「オートセーブのみ」を選べるようにする

【代替案】
セーブは自由のままにして、リセマラは本人の遊び方に任せる。

### P-11 性別と女子野球（未決定 → D-08）

【問題】
プレイヤーに女性を選べるか、女子野球の進路を扱うかが決まっていない。

【影響】
選べる場合は、進路と参加条件をデータで表す必要がある。後から足すと進路データの作り直しになる。

【推奨変更】

【代替案】
初期はプレイヤーを男性に限定し、構造だけ用意しておく。

### P-13 自分の現在能力の見せ方（未決定 → D-06）

【問題】
自分の現在能力を正確な数値で見せるかが決まっていない。

【影響】
正確な数値だと「数字を上げる作業」になりやすい。全部ぼかすと手応えがない。

【推奨変更】
- 測定できるもの（50m 走、球速、遠投、身長・体重、成績）は正確な数値
- 技術系の能力は同年代評価・カテゴリ評価の等級（A〜G）と「最近伸びている」などの傾向で表示（設計書 §4.12 の④）。指導者の評価や測定会で精度が上がる
- 潜在能力は表示しない

【代替案】
自分の現在能力は正確な数値で表示する。

### P-16 実在学校の情報が確認できない項目（新規 → D-17）

【問題】
実在学校の名前・所在地は確認しやすいが、偏差値・入試制度・野球部の詳細（監督・部員数・寮・設備）は、利用できる形で確認できない可能性が高い。一方で、ゲームの進路システムを動かすにはこれらの値が必要になる。

【影響】
確認できない項目を空のままにすると、その学校は進路の候補として機能しない。推測で埋めると「確認できない情報を実在の情報として登録しない」方針に反する。

【推奨変更】
確認できない項目は**層 B の「ゲーム内設定」**として生成し、実在の情報とは別の値として持つ。画面では「ゲーム内設定」であることが分かるように表示する（例：偏差値の横に印をつける、学校画面に「この学校の野球部情報はゲーム内設定です」と出す）。確認できた項目は `observed` として持ち、ゲーム内設定より優先する。

【代替案】
- 確認できた項目が一定以上ある学校だけを実在名にし、他は架空の学校にする
- 学校は名前と所在地だけ実在にし、他の項目はすべてゲーム内設定にする（最も単純）

### P-17 Android へのインストール方法（新規 → D-21）

【問題】
Android 実機で遊ぶには APK を作ってインストールする必要がある。作り方は、Expo のクラウドビルド（Expo のアカウントが必要。無料枠あり）と、PC 上でのローカルビルド（Android の開発環境が必要）の2通りある。

【影響】
Phase 2（最初の画面）までに決めれば、Phase 1 には影響しない。

【推奨変更】
Expo のクラウドビルドで APK を作り、端末にダウンロードしてインストールする（PC に Android の開発環境を入れなくてよい）。

【代替案】
PC でローカルビルドする。開発中は Expo Go アプリで動作確認する（ただし Expo Go では使えないライブラリがある）。

### P-18 JavaScript エンジンの違いによる計算結果のずれ（設計に反映済み・報告のみ）

【問題】
`Math.exp`・`Math.pow` などの計算結果は、JavaScript エンジンによって末尾の桁が異なることがある。Android（Hermes）でプレイしたセーブを Node のテストで続けると、同じ seed・同じ入力でも結果がずれる可能性がある。

【影響】
セーブ／ロードの決定性（§14.2）が「同じエンジンの中」でしか保証されない。後から気付くと、計算をすべて書き換える大規模な修正になる。

【推奨変更】
エンジンでは自前の決定的な数学関数だけを使い、組み込みの数学関数・`Math.random()`・現在時刻を lint で禁止する（設計書 §3.5 に反映済み）。ゲームの仕様は変わらないため、Phase 1 からこの規則で実装する。

【代替案】
決定性は同じエンジンの中だけで保証し、端末間の一致は求めない。

### P-19 「REALISTIC」という名前の重複（報告のみ → D-25）

【問題】
難易度（CASUAL / STANDARD / REALISTIC）と人生継続方式（REALISTIC / LEGACY）の両方に「REALISTIC」がある。

【影響】
画面で両方を選ぶとき、何を選んでいるか分かりにくい。

【推奨変更】
内部では別の名前（`difficulty` と `lifeMode`）で扱う（設計書 §3.7 に反映済み）。画面表示の名前は Phase 2 で開始画面を作るときに決める。例：人生継続方式を「寿命あり／レガシー」と表示する。

【代替案】
両方とも REALISTIC のまま表示し、説明文で区別する。

## Part 4. Phase 1 開始の条件

1. **専用リポジトリ `baseball-life-sim` の用意（P-01）**：コードの実装は専用リポジトリで始める。この作業環境からはリポジトリを作成できないため、空のリポジトリの作成と、Claude の GitHub 連携からのアクセス許可をお願いしたい。用意ができ次第、設計書を移して Phase 1 の段階 1-1（設計書 §16.5）から始める
2. それ以外に Phase 1 の開始を妨げる問題はない
